# CLAUDE.md

## Project overview

React + TypeScript app built with Vite 8 and Tailwind CSS 4. **Read [docs/architecture.md](docs/architecture.md) first**: it's the guide for people and agents alike, with the layers, the seam between pages and data, a walk through one page, and why. This file adds only what an agent needs on top.

- `src/components/primitives/`, `patterns/`, `domain/`: the component layers. Patterns and domain both sit on primitives and never import each other; pages put them together.
- `src/pages/`: one folder per screen (`src/pages/projects/`), holding `XPage.tsx` (draws, nothing else), its `XPage.query.tsx` wrapper (feeds it from the API), its story, `XPage.test.tsx` and `XPage.query.test.tsx`. Pages not yet moved are still flat in `src/pages/`; [docs/convergence.md](docs/convergence.md) tracks the move.
- `src/model/`: types, fixed vocabulary and pure functions. `src/fixtures/`: the fake records a server would send.
- `src/app/`: routing (`PageRoute.tsx` holds the table of which wrapper feeds each page), the shell's wrapper and app state.
- `src/api/`: the API client and a file of hooks per resource. `src/fake-api/`: the pretend Lightning server that answers it, seeded from fixtures and kept in localStorage. How they fit is in [docs/architecture.md](docs/architecture.md#the-api).

## Commands

- `npm run dev` — start dev server
- `npm run build` — typecheck and build
- `npm run lint` — run ESLint, including the layer rules
- `npm test` — run the tests (Vitest): `.test.ts` in Node (the fake server's lifecycles, helpers), `.test.tsx` in jsdom (pages and their wrappers)
- `npm run convergence` — the convergence counts (see docs/convergence.md)
- `npm run metrics` / `metrics:check` / `metrics:update` — the ratchet (see the guide)
- `npm run storybook` — start Storybook on port 6006
- `npm run build-storybook` — build Storybook static site

## Components and pages

The app is built from a component library in four layers, and Storybook is its catalogue.

- **Every UI element in the app must exist as a component with a story**, in the layer that fits what it knows. `primitives/` are the smallest pieces and know nothing about OpenFn. `patterns/` are the shape of a screen or a region of one, with no OpenFn nouns, so they're reusable anywhere. `domain/` is anything in OpenFn's words, from a status badge up to the workflow canvas. Buttons, cards, form fields, toggles, tables, badges, callouts, empty states, menus: if it renders on screen, it is a component.
- **Patterns get OpenFn content only through slots.** A pattern imports primitives and other patterns, never `domain/` or `src/model/` (model types are OpenFn nouns too), and its props are generic (`title`, `action`, `rows: T[]`, never `workflow` or `run`). Whoever uses the pattern imports the domain components and passes them in as `children` or `ReactNode` props: `<PageHeader breadcrumbs={<Breadcrumbs ... />} />`, `<Layout sidebar={(drawer) => <Sidebar {...drawer} />} logo={<InstanceLogo ... />}>`. That's what keeps a pattern usable for Credentials and Channels alike; the why is in [docs/architecture.md](docs/architecture.md#patterns-take-openfn-content-through-slots). If something is mostly shape but needs one OpenFn noun, turn that import into a slot; if that isn't small, it belongs in `domain/`.
- **Domain components draw with primitives only** (and other domain components), never a pattern. When one belongs inside a pattern's frame, the page draws the pattern and fills its slots with the domain pieces; where the pieces share state, the domain component takes a function as `children` and hands them over (`<CodeWorkspace>{(code) => <CodeLayout nav={code.nav} …>{code.main}</CodeLayout>}</CodeWorkspace>`, `<EditorToolbar>{(bar) => <EditorTopBar {...bar} />}</EditorToolbar>`). Before styling markup in a domain component, reach for the core primitives: `NavItem`, `Card`, `IconTile`, `Badge`, `Code`, `FormField`. The why is in [docs/architecture.md](docs/architecture.md#domain-draws-with-primitives).
- **Domain components carry meaning, not rules.** They know what colour "crashed" is or how a cron string reads, but who can delete, rename or retry arrives as a prop (`canDelete`, `onRetry`, or leaving `onRename` out on main), decided by the page's wrapper. Domain is one flat folder; subfolders by part of the product are fine if it gets hard to scan, with no import rules of their own.
- **Pages (`src/pages/XPage.tsx`) are composed from components only.** They should not define their own styled helpers (no local `Card`, `SaveButton`, `ToggleSwitch`, etc.) or hand-roll styled `<button>`/`<input>`/`<table>` markup.
- **Pages draw, and nothing else.** A page takes everything as props: `PageProps<Data>` (`node`, `ancestors`, `currentPath`, `data`) plus an `onX` callback for each thing the user can do. A server action returns a `Promise`; navigation is a plain callback. The page's props type, exported as `XPageProps`, is its contract: write it by hand, with a comment on every prop. Its `XPageData` lives beside it in the page file; a shape a component shares goes in its resource's `src/model/` file, named as in openfn-3-poc's `api/` (`ProjectSummary` in `model/projects.ts`). Never add to `src/model/page-data.ts`: it's being split up.
- **Data comes from the API.** A page on the API has an `XPage.query.tsx` wrapper that calls hooks from `src/api/<resource>.ts`; the hooks talk to the fake server in `src/fake-api/`, which follows openfn-3-poc's `api/` contract (ids are UUIDs, refusals are problem documents with a `code`, creates and deletes cascade as the API says). A new action is a route on the fake server (in its resource file, as `api/` documents it), a mutation in the resource's hooks that invalidates what it changed, and an `onX` that returns its promise. Areas `api/` doesn't cover go under `/api/demo/`, following `api/conventions.md`. Write a test of the lifecycle beside the route (`npm test`).
- **Every page has tests.** `XPage.test.tsx` draws the page with `renderPage` (`src/test/renderPage.tsx`), answers each `onX` with `resolve` or `reject`, and checks pending, success and the refusal under its field; lint holds it to the page's rules. `XPage.query.test.tsx` renders the wrapper on the fake server (`ApiProvider retry={false}`, `resetFakeApi()`, `setWait(0)`, `failNext` for a refusal). `src/pages/projects/` is the worked example.
- **Only wrappers read the router; wrappers don't read fixtures.** The page's wrapper reads the route, calls the hooks, implements the callbacks, and renders the page, with `pageFrame` from `src/app/page-frame.ts` for its node and crumbs. What the API can't give yet is left out and goes in [docs/api-gaps.md](docs/api-gaps.md); older wrappers that still read fixtures are counted by `npm run convergence`; register a new page's wrapper in `src/app/PageRoute.tsx` (the editor's is routed in `src/app/App.tsx`). Components and pages never import `src/fixtures/`, `src/app/` or `react-router-dom` (links go through the `Link` primitive or `TextLink`). Lint enforces all of this; don't silence it. The one exception is marked `debt:` and new work never adds one.
- **Need something that doesn't exist yet? Create the component first**, add its story, then use it in the page. If an existing component is close, extend it (add a prop or variant) rather than copying it.
- **Never disable a submit button to say a form isn't ready.** Keep it enabled; on submit, check the form and say what's missing under the field it's about (`FormField`'s `error`, "Enter a project name"), and focus that field. A disabled button can't be focused and doesn't say why. While its own action runs it says so ("Saving…") and is marked `aria-disabled`, not `disabled`, so it keeps focus and the label is read out; the handler ignores a second press. This holds for every form, modal and confirm.
- Settings pages use `SettingsLayout` (a breadcrumbs slot, title, `SettingsNav` side menu, content). Reuse it for any new settings-style page.

Existing building blocks to reach for: `PageContainer` (the centred, 1024px-max column `Layout` wraps every page outside the editor in; templates don't set their own page width), `PageHeader` (top of every page; pass it `<Breadcrumbs>` as `breadcrumbs`), `Button`, `IconButton` (every icon-only button: `ghost` for close, collapse, copy and ⋮, `toggle` for a pressed state), `Surface` (the frame of anything that floats: `raised` bars and cards, `floating` panels and dialogs, `popover` menus), `SearchInput`, `Card` (a settings section, or with `to`/`onClick` a whole-card link or button; `padding="sm"` in grids), `IconTile` (a glyph, logo or letters on a rounded square: list rows, feature cards, adaptor logos), `Code` (an id or a bit of code inside a sentence), `SectionHeading`, `FormField`, `FormControls` (`TextInput`, `TextArea`, `Select`, `RadioOption`), `ToggleSwitch`, `DataTable`, `ListRow`, `ChannelRow`, `ChannelView` (a channel's details, traffic and messages, in the project and the editor alike), `SegmentedControl` (`boxed` filters, `pill` view switchers), `FilterChip` (one filter over a list, saying what it's set to, e.g. "Workflow is any", with `FilterOptions`, `FilterChecklist` or `FilterDateRange` in its panel), `StatTile` (`compact` in narrow cards), `DropdownMenu` (actions from any trigger), `MenuButton`, `Picker`, `Modal`, `ConfirmModal`, `Badge` (`shape="tag"` for the small square note beside a name, e.g. a component's kind or "Read only"), `AdaptorLogo` (the one way to draw an adaptor or system: its logo, letters when there's no logo, a globe when we can't place it), `EntityPill` (an icon tile and a name in a bordered pill: every connected system, step adaptor, trigger and assistant reference, with `shape`, `size`, `tone` and a `trailing` slot; adaptors are always the round `pill`, on the canvas and in the code view alike), `StatusPill` (every run status, as a `pill`, `dot`, `icon` or explorer `mark`; never a `Badge`), `RunLabel` (the "● Run abc123 · detail" line naming a loaded run, with an optional Unload), `ComponentView` (a form, artifact, AI skill, document or static website's file, with Save) and `CollectionView` (a collection's keys), each `variant="page"` or `"pane"` like `ChannelView`, `ScrollPane` (a view shown in an editor's main area: fills it and scrolls), `Card`'s `actions` (controls beside its title) and `CodeEditor`'s `frame="box"` (a code box of its own height inside a card), `Callout`, `EmptyState`, `ProgressBar`, `BarChart`, `Donut`, `TextLink`, `NavItem` (every row of a list of places or choices, as a route link, off-site link or button, with an optional second line: `sidebar` in the side menu, `section` in `SettingsNav`, `tree` in the code explorer and lists like "Connect a system" and a project's components, `menu` in `DropdownMenu`, `MenuButton`, `Picker` and the account menu), `NavSection` (a group of `NavItem`s under a small heading), `SettingsNav`, `SettingsLayout`, `Breadcrumbs`. Menus and popovers close on an outside click or Escape through `usePopover` (or `useDismiss` when the open state is controlled) in `src/components/primitives/use-popover.ts`; don't hand-write that effect. Trigger kinds are named and drawn from `triggerTypes` in `src/model/workflow.ts` (label, short label, icon), and the run data sections (log, input, output) are `RunDataSection` from `panel-views.ts`; don't redeclare either. Button labels use sentence case ("New workflow", not "New Workflow").

**Lay out with primitives, not `className`.** The ratchet won't let `className` grow outside primitives, so new domain components and pages are built from `Stack` (vertical, `gap`, `divided`), `Inline` (horizontal, `justify`, `wrap`, `grow`, `stackOnMobile`) and `Text` (`tone`, `size`, `mono`, `truncate`, `nowrap`). Other pieces added with Lightning's core screens: `Checkbox`, `ExpandableRow` (a row that opens, in a `Card flush` + `Stack divided`), `ListHeader` (the select-all strip above such rows), `SelectionBar` (bulk actions for picked rows), `ActionMenu` (a row's ⋮), `Grid`, `Pagination`, `Swatch` / `SwatchPicker` (a picked colour), `DownloadButton`, `QrCode`; `FormField` takes `error` and `required`, `Select` takes `{ value, label }` options, `placeholder`, `fit` and `fullWidth`, and `ConfirmModal` takes a `confirmPhrase` to type.

### Feature flags

New features sit behind feature flags (`src/model/feature-flags.ts`; how they work is in [docs/architecture.md#feature-flags](docs/architecture.md#feature-flags)). With every flag off, the app is the redesign at about Lightning's scope: projects, workflows, channels, sandboxes, history, settings and the new editor, which is always on. **Anything you build that's new beyond Lightning belongs to a flag**: an existing one, or a new one in `featureFlags` with `requires` for what it builds on. Only wrappers, `src/app/` and the shell read flags (`useFlags()`). A wrapper leaves out the data or callback for what's off, and a page or component draws nothing for what it isn't given. Where something always renders, give it an optional prop (defaulting to on) and add a story for the off state. Tag a page's IA node with `flag` (gone when off) or `whenOff` (renamed when off), and a project nav section in `Sidebar` the same way. Check the "Lightning redesign" preset (`?flags=redesign`) as well as the full vision.

### Projects

Projects, their members and the people on the instance live on the API (`src/api/projects.ts`). A project's URL holds its UUID; an old link by a fixture's slug (`/projects/project-a/…`) redirects. Names are URL-safe (`planning-intake`), as Lightning's are; the create form shows what a typed name becomes. A project has exactly one owner and ownership can't be handed over; deleting one only schedules it, which takes it out of every list and refuses its pages until Admin settings cancels it. The project's environment is set when it's made. Pages not yet on the API find their fixture project with `fixtureProject(id)`, and `asProject` (`src/pages/project-records.query.ts`) fills a project from the API with its fixture's services, components and sandboxes until those move too. The shell (`src/app/Shell.query.tsx`) names the project from the API and keeps your recently opened projects in the browser (`src/app/recent-projects.ts`); `Shell.fixtures.tsx` still feeds stories.

### Project settings

A project's collections (`src/api/collections.ts`; items by name under `/collections/:name`), webhook auth methods (`src/api/webhook-auth.ts`) and history exports (`src/api/history-exports.ts`) are on the API, as are its members, MFA requirement and data retention. Collection names are unique in the project; deleting one deletes its items. A method's API key is made by the server and shown once, in the answer to creating it; which triggers a method guards is set on the workflows' triggers (`webhook_auth_method_ids`), and deleting a method takes it off them. An export is made in the background: the list polls until it's done. The GitHub connection is on the API too (`src/api/github.ts`): making one needs your account linked to GitHub, and a sandbox family can't sync one repo and branch twice.

### Your account

Your profile, email, password, API tokens, MFA and GitHub link are on the API (`src/api/account.ts`: `/api/me`, your own `PATCH /api/users/:id`, `/api/me/tokens`, `/api/me/mfa`). The account menu reads you from the API too. A new email is held as pending until it's confirmed; a new token is shown once; turning MFA on takes a code from the new secret and makes ten backup codes. The demo's session counts as stepped up, so the current password a form asks for isn't checked. A superuser can't schedule their own deletion. Admin settings' single sign-on is `/api/auth_provider`, which checks the discovery URL before saving.

### Channels

Channels and their recorded requests are on the API (`src/api/channels.ts`; `useProjectChannels` in `src/pages/channel-records.query.ts` names their credentials). A channel's id is a UUID (old slug links redirect); its name is unique in the project; every change bumps its `lock_version`, and a save over someone else's is refused (`concurrent_edit`). Turned off, it refuses requests; deleting it deletes its requests. Its client auth is the project's webhook auth methods, and its destination credential a project credential. The demo's own fields (kind, system, sample payload, a week's traffic, workflow) ride along beside Lightning's.

### Components

Every kind of project component besides workflows has create, read, update and delete, on the API, and one view that both its page in the project and the editor's explorer show, the way `ChannelView` does for channels. `useProjectComponents` (`src/pages/component-records.query.ts`) gives a wrapper the whole list (channels, collections and the rest) with their saves; trim it with `componentsFor` and `componentTypesFor` for the flags. Collections are Lightning's own (`src/api/collections.ts`: listed for owners and admins, keys written by editors and up through `/collections/:name/:key`), shown by `CollectionView`. Forms, artifacts, AI skills, documents and static websites are each one file (`src/model/project-components.ts`: a form or artifact is JSON, a skill or document Markdown, a website HTML), on the demo's own routes (`/api/demo/projects/:id/components`, `src/api/project-components.ts`): a type fixed when it's made, a name unique among that type in the project, a `lock_version` that refuses a stale save (`concurrent_edit`), and JSON that must parse. They're shown by `ComponentView`, an editor with Save. A component's page is `ComponentPage` (a channel's is still `ChannelPage`), fed by `ComponentPage.query.tsx`, which also sends old slug links on. The Components page's panel opens each kind's form (`ChannelFormModal`, `CollectionNameModal` or `ComponentFormModal`), and so does the explorer's + in a sandbox; the new one opens. With Build with AI on, the form offers to hand the kind to Create instead. Components belong to the project, not a sandbox, so the editor shows and changes its root project's. Fixture content is in `src/fixtures/project-components.ts`.

### Credentials

Credentials and OAuth clients are on the API (`src/api/credentials.ts`). A credential has one owner and reaches projects through links; a step points at the link (`JobNode.credentialId`, saved as the job's `project_credential_id`), so a step's credential is saved with the workflow. Linking to a project links its sandboxes too, and sandboxes use their project's links. Bodies are sent, never read back: the edit form gets each environment's values that aren't secret from `GET /api/credentials/:id/environments` (a demo extension, since `api/` never sends bodies), and a blank secret keeps the stored one. Deleting one that runs have used schedules it instead. A member who leaves a project takes their credentials' links there with them. The kinds of credential the form offers are the API's credential schemas: the picker reads only the list (`useCredentialSchemas`, `CredentialSchemaSummary`), and a type's JSON Schema is fetched once it's picked, or as a credential opens for editing (`useCredentialSchemaLoader`, passed down as `onLoadCredentialSchema`), and read into `CredentialField`s; raw JSON has no schema, so its one field is `rawCredentialSchema` in `model/credentials.ts`. The organisation's credentials on connected systems aren't API credentials yet.

### Workflows and sandboxes

Workflows, their versions and sandboxes live on the API (`src/api/workflows.ts`; the fake server's `workflows.ts` and `sandboxes.ts`). A workflow is stored as Lightning's document (jobs, triggers, edges, positions); `toDocument` and `fromDocument` in `src/model/workflow-document.ts` turn the canvas's graph into it and back. Every id is a UUID: seeded steps get theirs from their workflow's slug (`apiNodeId`), and a sandbox's copy from the step it was copied from (`cloneNodeId`), which is how the fixtures' run history is still drawn on the right steps. A sandbox is a child project: making one copies every workflow with its triggers off, and the editor shows the selected sandbox's copy (paired by name). In a sandbox the editor saves each edit to that copy (`onSaveWorkflow`, a moment after the change), "Go live" merges it into the sandbox's parent as a new version (`onPromote`), and the version picker lists the snapshots. The API's rules hold: a name unique in the project, no cycles, one enabled trigger and exactly one edge out of it, triggers never removed; a refused save shows in the editor's status bar. Turning a workflow on or off switches its trigger (not a new version); deleting marks it deleted. "New workflow" makes one at once, in the selected sandbox. The Sandboxes page reads each sandbox's changes from the API's merge preview. A workflow's runs are still the fixtures' (`fixtureWorkflow(id)` finds its slug) until runs move to the API.

### History

History (`HistoryPage`, a project's or, with Organizations on, every project's) is Lightning's work order history: `WorkOrderEntry` rows that open to each run's `RunEntry` (steps, retry from a step, inspect in the editor), search by id, dataclip name, input or log, and Lightning's filters as a row of `FilterChip`s in `HistoryFilterBar` (workflow, status (any number), received and last activity ranges, project across projects, a work order from a link; channel and outcome on the channel requests tab), all kept in the URL by the wrapper (`HistoryFilters` and `matchesFilters` in `src/model/history.ts`, `filtersFrom`/`paramsFor` in `HistoryPage.query.tsx`), and bulk retry, retry-from and cancel by Lightning's rules (`bulkActions` in `src/model/history.ts`), with a Channel requests tab (`ChannelRequestTable`). Its work orders, runs and channel requests come from the API (`src/api/work-orders.ts`, `useChannelRequests` in `src/api/channels.ts`), the same ones the editor reads: retrying (`/work_orders/retries`) adds a run to each work order on the server, on the workflow as it now stands, and a deleted workflow's are discarded; cancelling stops runs that haven't started; a run started in the editor is recorded when it finishes (`onRunFinished`, the demo standing in for Lightning's worker). A sandbox's copy of a workflow has its own runs, none to start with. Run, work order and dataclip ids are still the demo's short ones, not UUIDs, because the pages show them whole.

### Admin settings

Admin settings (`AdminSettingsPage`, at `/admin-settings`) is Lightning's superuser area, `/settings/*`: users, every project, the audit trail, single sign-on (OIDC), every collection and maintenance. It's core Lightning, so it has no flag, and it's instance-wide, so keep it apart from Organization settings (the flagged organisation concept). Its IA node is `superuserOnly`: the route table hides it unless the shell's `isSuperuser` (from `currentUserIsSuperuser` in `src/fixtures/user.ts`) is true, and `AccountMenu` only links to it with `showAdminSettings`. Its users, projects (with their members) and audit trail come from the API (`src/api/admin.ts`; the fake server's `users.ts`, `user-routes.ts`, `projects.ts` and `audit.ts`, seeded from `src/fixtures/admin.ts`), so a change there is what every page sees and lands in the audit trail. The audit trail is paged and filtered by the server (`useAuditTrail`), with its filters and page in the URL; only a text search reads the whole filtered trail (docs/api-gaps.md). Deletions are only ever scheduled, as the API has it: "Delete now" is left out. Every collection on the instance, the single sign-on provider and the instance itself (`useInstance`: its URL and deletion grace period) come from the API too; testing a provider before saving it and the maintenance jobs are on the demo's own routes (`/api/demo/auth_provider/test`, `/api/demo/maintenance`, `src/api/maintenance.ts`). The wrapper reads no fixtures. Helpers such as `projectOwnerError`, `authRedirectUri` and `filterAuditEvents` are in `src/model/admin.ts`. Reuse `AdminUserTable`, `UserFormModal`, `AdminProjectTable`, `ProjectFormModal`, `AuditTrail` (with `AuditChanges`), `AuthProviderForm`, `AdminCollectionTable` and `MaintenanceTaskCard`; for a long list use the `Pagination` primitive, for a typed confirmation `ConfirmModal`'s `confirmPhrase`, and for an expandable row `DataTable`'s `renderDetail`.

### Connected systems

The organisation's connected systems and their access grants are on the demo's own routes (`/api/demo/connected_systems`, `src/api/connected-systems.ts`; Lightning's API has none yet), following `api/conventions.md`. Adding one (by hand, from Systems or Overview, or from the X-Road directory) saves it and opens its page; editing it (`SystemFormModal`: name, description, API docs and, for a direct system, each environment's URL, keeping its credentials), revoking a grant and deleting a system go through the API, and it's the same list for the editor's "Connect a system". Old slug links redirect. The ecosystem map is still placed by hand in `src/fixtures/ecosystem.ts`; a seeded system that's deleted leaves it.

### Services

A project's published services are on the demo's own routes (`/api/demo/services`, `/api/demo/projects/:id/services`, `src/api/services.ts`). A service's id is a UUID (`apiServiceId`; old slug links redirect) and its code is the end of its address. Owners and admins set it Live or Draft, turn on MCP and publish it to X-Road (under its code unless it has its own); everyone else reads it, so the service page leaves those actions out. The catalog (`ServicesPage.query.tsx`) takes each workflow entry's status and how it can be called from the API, and drops one whose project is deleted; channels, systems' services and usage are still the fixtures'.

### Organization settings

The organisation is on the demo's own routes (`/api/demo/organization`, `src/api/organization.ts`; Lightning's API has no organisations). Members are invited by email with a role: someone already on the instance joins at once, anyone else shows as invited until they do. The organisation always keeps an owner (`last_owner`), and only an owner makes or unmakes one, so an admin is offered every role but Owner. Visibility defaults, who manages the Security Server and context layers (requested by URL, waiting for approval, unique) save there too; the rest of the X-Road identity is the X-Road operator's, read only from `GET /api/demo/organization/xroad` (`useOrganizationXRoad`, seeded from `orgXRoad`), and billing is read only. The page and its wrapper are in `src/pages/organization-settings/`; the organisation's types are in `src/model/organization.ts`. Owners and admins get the page's actions; for anyone else the wrapper leaves them out and the page reads only.

### Handbook

The handbook's files are on the demo's own routes (`/api/demo/handbook`, `src/api/handbook.ts`). Anyone in the organisation adds or removes one; a file's name is unique, its type is one the handbook takes, and together they fit its capacity, with a refusal shown in `FilesPanel`'s `notice`. The demo keeps a file's name and size, not its contents. The article is on the API too (`PUT /api/demo/handbook/article`, seeded from the fixture): Edit turns it into Markdown (`toMarkdown`/`fromMarkdown` in `src/model/handbook-markdown.ts`: `## ` sections, `- ` lists, `| Label | Detail |` facts, `[text](/path)` links), and the server refuses a section without a heading or one named twice and records who last edited it. The page and its wrapper are in `src/pages/handbook/`; the handbook's types (`Handbook`, `WikiSection`, `HandbookFile`) are in `src/model/handbook.ts`.

### X-Road

X-Road is a property of a connected system, never of a workflow. A system's `connection` (`src/model/connected-systems.ts`; the systems themselves are in `src/fixtures/connected-systems.ts`) is direct or via X-Road (a member, subsystem and service, a status track, an agreement); routing, headers and the organisation's identity come from the organisation's X-Road settings (`orgXRoad` in `src/fixtures/xroad.ts`, which also holds the directory (`listClients`) and the network; Organization settings reads them from the API, the system and service pages still from the fixture). Components get the settings, the member and the service as props; helpers that read them (`clientIdOf`, `findService`, `serviceIdOf`) are pure functions in `src/model/xroad.ts`. OpenFn is always a subsystem of the owning organisation. Show how a system is reached with `ConnectionMethodBadge` (`compact` on canvas cards) and an X-Road system's access with `XRoadAccessBadge`; reuse `XRoadStatusTrack`, `XRoadConnectionDetails`, `XRoadDirectory`, `XRoadCallDetails` (who called a run over X-Road), `PublishToXRoadModal`, `ServiceRecordList` (a service's catalogue record) and `CopyValue` (any value to paste elsewhere). Name services as actions ("Verify a national ID"), not resources.

### Ecosystem view

The systems page has a List | Ecosystem switch. The ecosystem is `EcosystemView`: a transport map (`EcosystemMap`) of the organisation's systems as stations (their adaptor logos) and the workflows between them as right-angled lines with runs moving along them, with `EcosystemPanel` beside it for the whole ecosystem or the picked workflow (a line diagram, trigger first), system or link. Lines are either Connections (one per pair of systems, coloured by health, weighted by runs) or Workflows (one per workflow in its own colour, side by side where they share a link). Systems reached over X-Road sit in an X-Road zone, and members calling a service you publish are drawn as stations too; this replaces the old X-Road network map. Stations, workflows and corners live in `src/fixtures/ecosystem.ts` (stations are placed by hand on a grid; add a corner in `ecosystemRoutes` for a link that can't be straight), and the geometry and numbers in `src/model/ecosystem-map.ts`.

### Workflow editor

The editor (its frame is the patterns `EditorShell`, `EditorTopBar`, `CanvasLayout`, `CodeLayout`, `EditorTray` and `EditorPanel`, everything that knows about workflows, `CodePaneHeader` and `EditorStatusBar` included, is in `src/components/domain/`, and its page is `src/pages/WorkflowEditorPage.tsx`) is laid out like an IDE: `EditorShell` (the top bar, the main surface, and the side column on the right, where the assistant lives a level above either view), `EditorToolbar` (whose groups the page puts in `EditorTopBar`: the `Fn` `WorkflowFileMenu`, `SandboxChip`, the workflow title (name • version, which opens the version `Picker`), Canvas/Code switcher, in code mode a `LoadedRunBar` for a loaded run, `RunMenuButton` with the main action, and the assistant toggle in its own group), then in the main surface either `CanvasLayout` (the canvas, with a bar pinned to its bottom and a card over its right) or `CodeLayout` (the code view, with its trays: `EditorPanel` under the code and an `EditorTray` for the details column on the right). Trays belong to the code view only. Keep the toolbar to those controls. On main, `ReadOnlyNotice` says the workflow is read-only: pinned to the bottom of the canvas (`CanvasLayout`'s `bottom` slot) with a link to edit in a sandbox, and as a tag in the code pane's top-right corner. **The canvas has no panel.** Pinned just above the workflow's top card (the canvas's `header`, so it pans with the workflow) sits `CanvasRunsBar`, which sets what the workflow shows: run history over a period (`PeriodPicker` with Off, 24h, 7d, 30d, plus the run and failure counts), just the workflow (Off), or a loaded run with a clear "Unload run" (`LoadedRunBar`, which goes back to the history; no Filter while a run is loaded). Its Filter opens `RunHistoryList` over the canvas for the period; the failed count opens it too. In a sandbox, hovering a card shows a + on its bottom edge that adds a step after it through `ConnectSystemPicker` ("Connect a system", in a `Modal`): a `SettingsNav` of Connected (the project's systems beside the built-in tools, the default), AI (generate, summarize, translate, classify, extract, and the models) and the categories in `src/fixtures/adaptor-catalog.ts`, which holds every adaptor; add new adaptors there, with their logo in `src/assets/adaptors/`. Clicking a card selects it and opens the inspector; double-clicking it, or its ⋮ menu's Edit, opens that node in code mode. The side UI is `StepInspector`, a compact card over the right edge (`CanvasLayout`'s `rightOverlay` slot) for the selected node, with three states that follow the bar: **config** (runs Off: name, adaptor and credential, or the trigger's type, URL and switch, plus the assistant's summary of the step's code from `src/fixtures/code-summaries.ts` with "See full code"); **stats** (run history: runs, failures and success rate as compact `StatTile`s, and `FailureBreakdown` with no period picker or scope switch, since the bar sets the period and the node sets the scope; on the trigger the numbers are the whole workflow's); **run** (a run loaded: `DataSnippet`s for the log, input and output, whose expand opens that view in the code view's panel, and an "Unload run" control). In code mode, anything about runs is a view in the panel: add it to `panel-views.ts` and `PanelViewId`, render its body in `WorkflowEditorPage` (which passes `panelViews` to `EditorPanel`), and the panel's tab bar, collapse and maximise come for free. The right dock belongs to the assistant, which always takes the outermost column. Layout (explorer, panel, panel view, details column, assistant, whether run history shows on the canvas) lives in `src/components/domain/editor-layout.ts`, is remembered across workflows, and is edited only from `LayoutMenu` (the ⋯ at the top-right corner of the code area, just left of the X that closes the code view back to the canvas, with a checkbox for the bottom and right panels; the explorer is Ctrl/⌘ + B and the assistant has its toolbar button) or, for the canvas's run history, the runs bar. Never add layout toggles to the toolbar. Code mode is `CodeWorkspace`, whose pieces the page lays out in `CodeLayout` (and the details column in an `EditorTray`), since domain doesn't draw patterns: `EditorExplorer` on the left in Workflow / Steps / Components groups (Workflow lists its files and, under service.md, Health; each adds from a + on its heading: a new doc, a step, or the `AddComponentPanel` picker in a `Modal`; steps show their adaptor icon on the left); `CodePaneHeader` (for a step, its adaptor pill, which opens Config, then just the step name; a path for anything else) + `CodeEditor` + `EditorStatusBar` in the middle, where an item that isn't text passes `CodeWorkspace` a `pane` that takes the editor's place; the details column on the right with its views, Config (`StepConfigPanel`, `TriggerConfigPanel`, `WorkflowSettingsPanel` or `FileDetailsPanel`) and, for a step, Snippets, the default view (`AdaptorReferencePanel`: the step's own adaptor only, as `SnippetCard`s that insert at the cursor via the `CodeEditor` handle) and, only while a run is loaded, I/O (`RunIOPanel`: the step's input over its output, each at half the height, or on the trigger the run's input, whose expand opens that view in the bottom panel). Running from a step lives in the toolbar's `RunMenuButton`, not the code pane. Adaptor snippets live in `src/fixtures/adaptor-reference.ts` and surface only through `AdaptorReferencePanel`. Health, opened from the explorer, is `WorkflowHealth` in that `pane`. A collection in the explorer's Components opens `CollectionView` in that `pane`, and a form, artifact, AI skill, document or static website `ComponentView` (each the same view as its page in the project, editable there too). A channel in the explorer's Components opens `ChannelView` in that `pane` (its system, endpoint, a week's traffic, recent messages, where one from a run loads it, and its message shape, from the API: `src/api/channels.ts`, with the demo's extra fields beside Lightning's), with its kind, system and method in the details column. The project's page for the channel (`ChannelPage`, at `/projects/:project/components/:channel`) is the same `ChannelView` with `variant="page"` under a `PageHeader`, where loading a run opens the editor with it; keep the two in step by changing `ChannelView`, not either host. Channel kinds (read, write, event) are drawn from `channelTypeConfig` in `src/components/domain/channel-types.ts`. A page like it opens with the bottom and right panels hidden; showing them from the ⋯ menu lasts while it stays open, and opening a code item brings back the remembered layout. It shows the whole workflow's run history (every version, however runs started) for the same period as the runs bar, from `workflowHealth` in `src/model/runs.ts`, with work order outcomes (`Donut`), runs and failed runs over time (`BarChart`), steps with failures and failures by reason (`FailureBreakdown`), where picking a run loads it and opens the step it failed at.

Run counts on the canvas must add up down the graph: `runActivity` counts a run only along the path it walked from the trigger on the graph being shown, so the trigger counts every run, each step counts exactly what its incoming connectors carried, and no count grows as the workflow goes on. Runs that didn't walk this graph from its trigger (another version, a retry from a step) are left out of the counts, totals included, and the runs bar's list says how many.

## Colours

Every colour goes through the design system: Tailwind colour utilities (`bg-*`, `text-*`, `border-*`, `fill-*`, `stroke-*`), which resolve to theme tokens the Style Picker re-skins, or a named CSS variable in `src/theme/theme.css`. No hex, `rgb()` or `hsl()` literals in components or templates, including SVG `fill`/`stroke` attributes and inline styles.

## Storybook

Every UI component and template has a corresponding `.stories.tsx` file next to it. **When you add, modify, or delete a component, you must update its Storybook story to match.** Specifically:

- **New component** → create a `.stories.tsx` file alongside it with at least a default story and any meaningful variants.
- **Changed props/API** → update the existing story args and variants to reflect the new interface.
- **Deleted component** → delete the corresponding `.stories.tsx` file.
- **Router-dependent components** → use the `withRouter` decorator from `src/stories/decorators.tsx`.
- Stories should use fixtures from `src/fixtures/` when possible rather than inventing inline fixtures.

Run `npm run build-storybook` to verify stories compile. This also runs in CI on every PR.
