# CLAUDE.md

## Project overview

React + TypeScript app built with Vite 8 and Tailwind CSS 4. **Read [docs/architecture.md](docs/architecture.md) first**: it's the guide for people and agents alike, with the layers, the seam between pages and data, a walk through one page, and why. This file adds only what an agent needs on top.

- `src/components/primitives/`, `patterns/`, `domain/`: the component layers. Patterns and domain both sit on primitives and never import each other; pages put them together.
- `src/pages/`: one folder per screen (`src/pages/projects/`), holding `XPage.tsx` (draws, nothing else), its `XPage.query.tsx` wrapper (feeds it from the API), its story, `XPage.test.tsx` and `XPage.query.test.tsx`. Pages not yet moved are still flat in `src/pages/`; [docs/convergence.md](docs/convergence.md) tracks the move.
- `src/model/`: types, fixed vocabulary and pure functions. `src/fixtures/`: the fake records a server would send.
- `src/app/`: routing (`PageRoute.tsx` holds the table of which wrapper feeds each page), the shell's wrapper and app state.
- `src/api/`: the API client and a file of hooks per resource. `src/fake-api/`: the pretend Lightning server that answers it, seeded from fixtures and kept in localStorage. `src/api/source.ts` is the one switch between them and a real Lightning (only the `--mode lightning` build lightning-full-api serves at `/v3` can reach one, and there the demo settings' Data tab chooses, at runtime, between Lightning and the fixtures; [docs/lightning-backend.md](docs/lightning-backend.md)); pages, components and wrappers never know which is answering (only `src/app/` reads `apiSource`, for signing in, the reset, the Data tab, recent projects and Status). The two never mix: on Lightning the fake server answers only `/api/demo/` and starts empty, so whatever Lightning doesn't have shows empty. How they fit is in [docs/architecture.md](docs/architecture.md#the-api).

## Commands

- `npm run dev` — start dev server
- `npm run dev:lightning` — the dev server on a Lightning running at `localhost:4000`, at `localhost:5173/v3/` (docs/lightning-backend.md)
- `npm run build` — typecheck and build
- `npm run lint` — run ESLint, including the layer rules
- `npm test` — run the tests (Vitest): `.test.ts` in Node (the fake server's lifecycles, helpers), `.test.tsx` in jsdom (pages and their wrappers)
- `npm run convergence` — the convergence counts (see docs/convergence.md)
- `npm run metrics` / `metrics:check` / `metrics:update` — the ratchet (see the guide)
- `npm run storybook` — start Storybook on port 6006
- `npm run build-storybook` — build Storybook static site

**Design system docs** live in the app at `/docs` (`#/docs` in the browser; `src/docs/`, lazy loaded): an introduction for developers modelled on GitHub's Primer docs, built from the library itself. Its component reference is read from the source at build time (`scripts/component-catalog.ts`, served as `virtual:component-catalog`), so a component's JSDoc and its props' comments are what the docs show: write them well. When a new rule or pattern lands, add it to the right page there too; hand-written guidance for a component goes in `src/docs/content/components/guides.tsx`.

## Components and pages

The app is built from a component library in four layers, and Storybook is its catalogue.

- **Every UI element in the app must exist as a component with a story**, in the layer that fits what it knows. `primitives/` are the smallest pieces and know nothing about OpenFn. `patterns/` are the shape of a screen or a region of one, with no OpenFn nouns, so they're reusable anywhere. `domain/` is anything in OpenFn's words, from a status badge up to the workflow canvas. Buttons, cards, form fields, toggles, tables, badges, callouts, empty states, menus: if it renders on screen, it is a component.
- **Patterns get OpenFn content only through slots.** A pattern imports primitives and other patterns, never `domain/` or `src/model/` (model types are OpenFn nouns too), and its props are generic (`title`, `action`, `rows: T[]`, never `workflow` or `run`). Whoever uses the pattern imports the domain components and passes them in as `children` or `ReactNode` props: `<PageHeader breadcrumbs={<Breadcrumbs ... />} />`, `<Layout sidebar={(drawer) => <Sidebar {...drawer} />} logo={<InstanceLogo ... />}>`. That's what keeps a pattern usable for Credentials and Channels alike; the why is in [docs/architecture.md](docs/architecture.md#patterns-take-openfn-content-through-slots). If something is mostly shape but needs one OpenFn noun, turn that import into a slot; if that isn't small, it belongs in `domain/`.
- **Domain components draw with primitives only** (and other domain components), never a pattern. When one belongs inside a pattern's frame, the page draws the pattern and fills its slots with the domain pieces; where the pieces share state, the domain component takes a function as `children` and hands them over (`<CodeWorkspace>{(code) => <CodeLayout nav={code.nav} …>{code.main}</CodeLayout>}</CodeWorkspace>`, `<EditorToolbar>{(bar) => <EditorTopBar {...bar} />}</EditorToolbar>`). Before styling markup in a domain component, reach for the core primitives: `NavItem`, `Card`, `IconTile`, `Badge`, `Code`, `FormField`. The why is in [docs/architecture.md](docs/architecture.md#domain-draws-with-primitives).
- **Domain components carry meaning, not rules.** They know what colour "crashed" is or how a cron string reads, but who can delete, rename or retry arrives as a prop (`canDelete`, `onRetry`, or leaving `onRename` out on main), decided by the page's wrapper. Domain is one flat folder; subfolders by part of the product are fine if it gets hard to scan, with no import rules of their own.
- **Pages (`src/pages/XPage.tsx`) are composed from components only.** They should not define their own styled helpers (no local `Card`, `SaveButton`, `ToggleSwitch`, etc.) or hand-roll styled `<button>`/`<input>`/`<table>` markup.
- **Pages draw, and nothing else.** A page takes everything as props: `PageProps<Data>` (`node`, `ancestors`, `currentPath`, `data`) plus an `onX` callback for each thing the user can do. A server action returns a `Promise`; navigation is a plain callback. The page's props type, exported as `XPageProps`, is its contract: write it by hand, with a comment on every prop. Its `XPageData` lives beside it in the page file; a shape a component shares goes in its resource's `src/model/` file, named as in openfn-3-poc's `api/` (`ProjectSummary` in `model/projects.ts`). Never add to `src/model/page-data.ts`: it's being split up.
- **Data comes from the API.** A page on the API has an `XPage.query.tsx` wrapper that calls hooks from `src/api/<resource>.ts`; the hooks talk to the fake server in `src/fake-api/`, which follows openfn-3-poc's `api/` contract (ids are UUIDs, refusals are problem documents with a `code`, creates and deletes cascade as the API says). A new action is a route on the fake server (in its resource file, as `api/` documents it), a mutation in the resource's hooks that invalidates what it changed, and an `onX` that returns its promise. Areas `api/` doesn't cover go under `/api/demo/`, following `api/conventions.md`. Write a test of the lifecycle beside the route (`npm test`).
- **Every page has tests.** `XPage.test.tsx` draws the page with `renderPage` (`src/test/renderPage.tsx`), answers each `onX` with `resolve` or `reject`, and checks pending, success and the refusal under its field; lint holds it to the page's rules. `XPage.query.test.tsx` renders the wrapper on the fake server (`ApiProvider retry={false}`, `resetFakeApi()`, `setWait(0)`, `failNext` for a refusal). `src/pages/projects/` is the worked example.
- **Only wrappers read the router; wrappers don't read fixtures.** The page's wrapper reads the route, calls the hooks, implements the callbacks, and renders the page, with `pageFrame` from `src/app/page-frame.ts` for its node and crumbs. What the API can't give yet is left out and goes in [docs/api-gaps.md](docs/api-gaps.md); older wrappers that still read fixtures are counted by `npm run convergence`; register a new page's wrapper in `src/app/PageRoute.tsx` (the editor's is routed in `src/app/App.tsx`). Components and pages never import `src/fixtures/`, `src/app/` or `react-router-dom` (links go through the `Link` primitive or `TextLink`). Lint enforces all of this; don't silence it. The one exception is marked `debt:` and new work never adds one.
- **Need something that doesn't exist yet? Create the component first**, add its story, then use it in the page. If an existing component is close, extend it (add a prop or variant) rather than copying it.
- **Never disable a submit button to say a form isn't ready.** Keep it enabled; on submit, check the form and say what's missing under the field it's about (`FormField`'s `error`, "Enter a project name"), and focus that field. A disabled button can't be focused and doesn't say why. While its own action runs it says so ("Saving…") and is marked `aria-disabled`, not `disabled`, so it keeps focus and the label is read out; the handler ignores a second press. This holds for every form, modal and confirm.
- **What an action just did is a toast, never a banner in the page.** Saved, created, deleted, or refused with the server's reason: the wrapper says it once with `useAnnounceOutcome` (`announcing(promise, { success, failure })`, which hands the promise back so the page still shows it pending) or `useAnnounce` (`announce({ tone: "success" | "error" | "info", message, detail })`), both from `src/app/announce.ts`. `AnnouncementsProvider` (`src/app/announcements.tsx`) wraps the app in `main.tsx` and draws the `ToastStack`: dismissible, stacked bottom right, successes go by themselves and errors stay, read out politely or at once. Pages never call it: they `.catch` a refusal quietly (the wrapper said why) and keep their pending state. A form's problems still go under its fields, so a form's wrapper announces only `success`. Query tests that check a toast wrap the wrapper in `AnnouncementsProvider` and look in `role="alert"` or `role="status"`. A `Callout` is for what's true of the page (a channel that's off), not for what just happened. The rules are in the docs at `/docs/guidelines/notifications`.
- Settings pages use `SettingsLayout` (a breadcrumbs slot, title, `SettingsNav` side menu, content). Reuse it for any new settings-style page.

Existing building blocks to reach for: `PageContainer` (the centred, 1024px-max column `Layout` wraps every page outside the editor in; templates don't set their own page width), `PageHeader` (top of every page; pass it `<Breadcrumbs>` as `breadcrumbs`), `ListPage` (every page that lists things, in one order: `header`, an optional `intro` that sits above the `toolbar` and changes with its view, the `toolbar` (search, sort, filters, view switch; never in a heading or the header's actions), the list as children or `empty` when `isEmpty` (a list page doesn't count its rows; a `ListGroup` heading carries its count), and `after` for sections that follow, each under a default `SectionHeading`; modals sit beside it), `ListRow` (every full-width row of a list page: the whole row opens it, with a pointer cursor and no chevron, and its ⋮ `menu` on the right starts with Open; pass `menu={{}}` while a row has no actions, `menu={{ items, onSelect }}` to add them, and leave it out in pickers), `ListGroup` (one group of rows inside a list, under the small uppercase heading with an optional `count` and `description`; groups go in a `Stack gap="xl"`, and a list never heads its groups any other way), `Button`, `IconButton` (every icon-only button: `ghost` for close, collapse, copy and ⋮, `toggle` for a pressed state), `Surface` (the frame of anything that floats: `raised` bars and cards, `floating` panels and dialogs, `popover` menus), `SearchInput`, `Card` (a settings section, or with `to`/`onClick` a whole-card link or button; `padding="sm"` in grids), `IconTile` (a glyph, logo or letters on a rounded square: list rows, feature cards, adaptor logos), `Code` (an id or a bit of code inside a sentence), `SectionHeading`, `FormField`, `FormControls` (`TextInput`, `TextArea`, `Select`, `RadioOption`), `ToggleSwitch`, `DataTable`, `ListRow`, `ChannelRow`, `ChannelView` (a channel's details, traffic and messages, in the project and the editor alike), `SegmentedControl` (`boxed` filters, `pill` view switchers), `FilterChip` (one filter over a list, saying what it's set to, e.g. "Workflow is any", with `FilterOptions`, `FilterChecklist` or `FilterDateRange` in its panel), `StatTile` (`compact` in narrow cards), `DropdownMenu` (actions from any trigger), `MenuButton`, `Picker`, `Modal`, `ConfirmModal`, `Badge` (`shape="tag"` for the small square note beside a name, e.g. a component's kind or "Read only"), `AdaptorLogo` (the one way to draw an adaptor or system: its logo, letters when there's no logo, a globe when we can't place it), `EntityPill` (an icon tile and a name in a bordered pill: every connected system, step adaptor, trigger and assistant reference, with `shape`, `size`, `tone` and a `trailing` slot; adaptors are always the round `pill`, on the canvas and in the code view alike), `StatusPill` (every run status, as a `pill`, `dot`, `icon` or explorer `mark`; never a `Badge`), `RunLabel` (the "● Run abc123 · detail" line naming a loaded run, with an optional Unload), `ComponentView` (a form, artifact, AI skill, document or static website's file, with Save) and `CollectionView` (a collection's keys), each `variant="page"` or `"pane"` like `ChannelView`, `ScrollPane` (a view shown in an editor's main area: fills it and scrolls), `Card`'s `actions` (controls beside its title) and `CodeEditor`'s `frame="box"` (a code box of its own height inside a card), `Markdown` (any Markdown drawn as it reads: the handbook's article, a workflow's docs, an AI skill or document) and `MarkdownEditor` (that, with Edit, Cancel and Save over the code editor; don't write another renderer), `Callout`, `EmptyState`, `ProgressBar`, `BarChart`, `Donut`, `TextLink`, `NavItem` (every row of a list of places or choices, as a route link, off-site link or button, with an optional second line: `sidebar` in the side menu, `section` in `SettingsNav`, `tree` in the code explorer and lists like "Connect a system" and a project's components, `menu` in `DropdownMenu`, `MenuButton`, `Picker` and the account menu), `NavSection` (a group of `NavItem`s under a small heading), `SettingsNav`, `SettingsLayout`, `Breadcrumbs`. Menus open in a `FloatingLayer` (`DropdownMenu` does it for you, so every ⋮ and `MenuButton`), drawn at the end of the page so a table, card or scroll pane can't crop them. Menus and popovers close on an outside click or Escape through `usePopover` (or `useDismiss` when the open state is controlled) in `src/components/primitives/use-popover.ts`; don't hand-write that effect. Trigger kinds are named and drawn from `triggerTypes` in `src/model/workflow.ts` (label, short label, icon), and the run data sections (log, input, output) are `RunDataSection` from `panel-views.ts`; don't redeclare either. **Lay out with primitives, not `className`.** The ratchet won't let `className` grow outside primitives, so new domain components and pages are built from `Stack` (vertical, `gap`, `divided`), `Inline` (horizontal, `justify`, `wrap`, `grow`, `stackOnMobile`) and `Text` (`tone`, `size`, `mono`, `truncate`, `nowrap`). Other pieces added with Lightning's core screens: `Checkbox`, `ExpandableRow` (a row that opens, in a `Card flush` + `Stack divided`), `ListHeader` (the select-all strip above such rows), `SelectionBar` (bulk actions for picked rows), `ActionMenu` (a row's ⋮), `Grid`, `Pagination`, `Swatch` / `SwatchPicker` (a picked colour), `DownloadButton`, `QrCode`; `FormField` takes `error` and `required`, `Select` takes `{ value, label }` options, `placeholder`, `fit` and `fullWidth`, and `ConfirmModal` takes a `confirmPhrase` to type.

### Feature flags

New features sit behind feature flags (`src/model/feature-flags.ts`; how they work is in [docs/architecture.md#feature-flags](docs/architecture.md#feature-flags)). With every flag off, the app is the redesign at about Lightning's scope: projects, workflows, channels, sandboxes, history, settings and the new editor, which is always on. **Anything you build that's new beyond Lightning belongs to a flag**: an existing one, or a new one in `featureFlags` with `requires` for what it builds on. Only wrappers, `src/app/` and the shell read flags (`useFlags()`). A wrapper leaves out the data or callback for what's off, and a page or component draws nothing for what it isn't given. Where something always renders, give it an optional prop (defaulting to on) and add a story for the off state. Tag a page's IA node with `flag` (gone when off) or `whenOff` (renamed when off), and a project nav section in `Sidebar` the same way. Check the "Lightning redesign" preset (`?flags=redesign`) as well as the full vision.

### Projects

Projects, their members and the people on the instance live on the API (`src/api/projects.ts`). A project's URL holds its UUID; an old link by a fixture's slug (`/projects/project-a/…`) redirects. Names are URL-safe (`planning-intake`), as Lightning's are; the create form shows what a typed name becomes. A project has exactly one owner and ownership can't be handed over; deleting one only schedules it, which takes it out of every list and refuses its pages until Admin settings cancels it. The project's environment is set when it's made. Pages not yet on the API find their fixture project with `fixtureProject(id)`; the shell's project is `asProject` (`src/model/projects.ts`), the API's project with its sandboxes and no services or components. A workflow's row on Workflows and Overview is `asListItem` (`src/model/workflow-list.ts`), from the API alone: api/ workflows have no description or members, so rows leave them out. The shell (`src/app/Shell.query.tsx`) takes the instance (`useInstance`; named by its URL's host where the API gives no name), you and whether you're a superuser (`useMe`) and the project's name from the API, leaving each out of the chrome until it's loaded, and keeps your recently opened projects in the browser (`src/app/recent-projects.ts`); `Shell.fixtures.tsx` still feeds stories. The project bar (`ProjectContextBar`) draws the editor's own `SandboxChip`, with the selected sandbox's changes from its merge preview (`previewChanges`), beside a project `Picker` at `size="sm"` so both bars' controls are one height; switching project there opens the other project on main (`onSwitchProject`). Sandbox names are unique only among a parent's own sandboxes, so pickers list them through `sandboxNames` (once each), and a new sandbox's name is checked as the slug it becomes.

### Project settings

A project's collections (`src/api/collections.ts`; items by name under `/collections/:name`), webhook auth methods (`src/api/webhook-auth.ts`) and history exports (`src/api/history-exports.ts`) are on the API, as are its members, MFA requirement and data retention. Collection names are unique in the project; deleting one deletes its items. A method's API key is made by the server and shown once, in the answer to creating it; which triggers a method guards is set on the workflows' triggers (`webhook_auth_method_ids`), and deleting a method takes it off them. An export is made in the background: the list polls until it's done. The GitHub connection is on the API too (`src/api/github.ts`): making one needs your account linked to GitHub, and a sandbox family can't sync one repo and branch twice. Its Credentials are the ones linked to the project (`useProjectCredentials`, named by the credential schemas); Export project is `GET /api/provision/yaml` (`src/api/provisioning.ts`) and an export's download its `download_url`, both fetched with `getFile` (`src/api/client.ts`), the one way to fetch an answer that isn't JSON. The page and its wrapper are in `src/pages/project-settings/`; its types are in `model/projects.ts` (collaborators, data storage), `model/webhooks.ts`, `model/github-sync.ts` and `model/work-orders.ts`, named as in api/.

### Your account

Your profile, email, password, API tokens, MFA and GitHub link are on the API (`src/api/account.ts`: `/api/me`, your own `PATCH /api/users/:id`, `/api/me/tokens`, `/api/me/mfa`). The account menu reads you from the API too. A new email is held as pending until it's confirmed; a new token is shown once; turning MFA on takes a code from the new secret and makes ten backup codes. Changing your email or password needs a stepped-up session, as on Lightning: the form sends the current password it asks for to `POST /api/session` first (the fake takes any but an empty one), and a wrong one is said under that field. Making a token, turning MFA off and deleting your account still don't ask. A superuser can't schedule their own deletion. Admin settings' single sign-on is `/api/auth_provider`, which checks the discovery URL before saving.

### Channels

Channels and their recorded requests are on the API (`src/api/channels.ts`; `useProjectChannels` in `src/pages/channel-records.query.ts` names their credentials). A channel's id is a UUID (old slug links redirect); its name is unique in the project; every change bumps its `lock_version`, and a save over someone else's is refused (`concurrent_edit`). Turned off, it refuses requests; deleting it deletes its requests. Its client auth is the project's webhook auth methods, and its destination credential a project credential. The demo's own fields (kind, system, sample payload, a week's traffic, workflow) ride along beside Lightning's.

### Components

Every kind of project component besides workflows has create, read, update and delete, on the API, and one view that both its page in the project and the editor's explorer show, the way `ChannelView` does for channels. `useProjectComponents` (`src/pages/component-records.query.ts`) gives a wrapper the whole list (channels, collections and the rest) with their saves; trim it with `componentsFor` and `componentTypesFor` (`src/model/component-types.ts`) for the flags. Collections are Lightning's own (`src/api/collections.ts`: listed for owners and admins, keys written by editors and up through `/collections/:name/:key`), shown by `CollectionView`. Forms, artifacts, AI skills, documents and static websites are each one file (`src/model/project-components.ts`: a form or artifact is JSON, a skill or document Markdown, a website HTML), on the demo's own routes (`/api/demo/projects/:id/components`, `src/api/project-components.ts`): a type fixed when it's made, a name unique among that type in the project, a `lock_version` that refuses a stale save (`concurrent_edit`), and JSON that must parse. They're shown by `ComponentView`, an editor with Save. A component's page is `ComponentPage` (a channel's is still `ChannelPage`), both in `src/pages/component/`, fed by `ComponentPage.query.tsx`; an old slug link is sent on by routing (`src/app/component-links.ts`), so the wrapper reads no fixtures. The Components page's panel opens each kind's form (`ChannelFormModal`, `CollectionNameModal` or `ComponentFormModal`), and so does the explorer's + in a sandbox; the new one opens. With Build with AI on, the form offers to hand the kind to Create instead. Components belong to a project, not to a workflow, and a sandbox is a copy of its project, components included: making one copies each of the parent's into it (`copyComponentsInto` in the fake server's `sandboxes.ts`; the fixtures' sandboxes are seeded the same way through `withSandboxCopies`), the editor shows and changes the selected sandbox's own, and a merge brings its new and changed ones back to the target with its workflows, pairing them by kind and name and never deleting the target's. The merge preview lists them (`components`), and the sandbox chip counts them with the workflow's changes (`useSandboxComponentChanges`, `componentChanges`). A channel's copy has no requests or traffic and points at the sandbox's copy of its workflow, and a merge keeps the target's switch and traffic; Lightning doesn't copy channels yet, so that part is the demo's. Collections follow Lightning: a sandbox gets an empty collection of the same name for each of its parent's (names are copied, keys never are), its runs read and write its own, and a merge creates the ones only the sandbox has, empty, and never deletes the parent's. Since a sandbox has collections of the same names, an item route given only a name is ambiguous (`ambiguous_name`): always send `project_id`. A component's page in the project shows main's, so the editor only offers "Open in project" on main. Fixture content is in `src/fixtures/project-components.ts`.

### Environment variables

A project's environment variables are on the demo's own routes (`/api/demo/projects/:id/env_vars`, `src/api/env-vars.ts`; Lightning's API has none), behind the Environment variables flag (which needs Workflow docs). Every project has its own, sandboxes included: making a sandbox copies its parent's (each remembers the one it came from, `copied_from`), a run in the sandbox uses the sandbox's values for its environment (a staging sandbox's staging values), and a merge brings its new and changed ones back to the target, never deleting any. The editor lists them under Workflow in the explorer, opening `EnvVarsView` in the code pane: `EnvVarForm` adds them a key and value a row at a time, Railway and Vercel style (pasting a `.env` into a key fills a row for each line), and each `EnvVarRow` opens to edit in place. A variable is set for one or more environments (`EnvironmentChecklist`), and a key can be set once in each, so it can hold a different value in production than in staging or mock. A secret's value is never sent back: a blank value keeps it, and a secret can't be made plain again. Editors and up change them. The rules are in `src/model/env-vars.ts`; the seeds in `src/fixtures/env-vars.ts`.

### Test cases

A workflow's test cases are on the demo's own routes (`/api/demo/projects/:id/test_cases?workflow_id=…`, `src/api/test-cases.ts`; Lightning's API has none), behind the Test cases flag (which needs Workflow docs). A test is a scenario in plain words (`src/model/test-cases.ts`): a name unique in the workflow, what goes in and what should come out, and the step it starts at and stops after (left out: the first step and the final output; the end must be reachable from the start). The assistant runs it (`…/:id/runs`): it makes an input to match the input's description, or takes a saved dataclip, runs the workflow between the two steps, and checks what came out by judging it against the output's description, running the test's deterministic tests, or both (at least one). "Generate from spec" (`…/generations`) has the assistant sync the tests with spec.md: a test with deterministic tests (and no judgement) for each requirement nothing covers yet, and a test whose requirement has left the spec says so. The assistant panel offers the same as "Generate tests from spec" (its ⋮ menu, and under the suggestions before there's a conversation; `onGenerateTests`): its reply (`testGenerationReply`) lists the tests it wrote, and "Open test cases" opens them. The editor lists Test cases under Saved dataclips in the explorer's Workflow group, opening `TestCasesView` in the code pane, with "Run all tests" at the top and a Run on each; `TestCaseFormModal` writes and edits one, also from "Add to workflow". Tests belong to the workflow, so they're written in a sandbox and run anywhere you could run it: making a sandbox copies them (without results), and a merge brings its new and changed ones back, deleting none. A test run isn't a work order, so it isn't in History (docs/api-gaps.md). The national ID workflow's tests and the plan the assistant writes them from are in `src/fixtures/test-cases.ts`.

### Credentials

Credentials and OAuth clients are on the API (`src/api/credentials.ts`). A credential has one owner and reaches projects through links; a step points at the link (`JobNode.credentialId`, saved as the job's `project_credential_id`), so a step's credential is saved with the workflow. Linking to a project links its sandboxes too, and sandboxes use their project's links. Bodies are sent, never read back: the edit form gets each environment's values that aren't secret from `GET /api/credentials/:id/environments` (a demo extension, since `api/` never sends bodies), and a blank secret keeps the stored one. Deleting one that runs have used schedules it instead. A member who leaves a project takes their credentials' links there with them. The kinds of credential the form offers are the API's credential schemas: the picker reads only the list (`useCredentialSchemas`, `CredentialSchemaSummary`), and a type's JSON Schema is fetched once it's picked, or as a credential opens for editing (`useCredentialSchemaLoader`, passed down as `onLoadCredentialSchema`), and read into `CredentialField`s; raw JSON has no schema, so its one field is `rawCredentialSchema` in `model/credentials.ts`. The organisation's credentials on connected systems aren't API credentials yet. In the editor a step's credential is picked in one click: its Config (`StepConfigPanel`, via `StepCredentialPicker`) lists the project's credentials on the step's adaptor with values for where it runs (the sandbox's environment, or production on main; `credentialsForStep` in `src/model/step-credentials.ts`), each with Add, and New credential opens `CredentialFormModal` set to that kind, the environment and the project (`onCreateCredential`, which resolves with the new link). A step that needs a credential and has none (`stepMissingCredential`: its adaptor needs one and its system isn't reached over X-Road) shows Connect on its canvas card in a sandbox, which opens it in code with Config scrolled to the credential.

### Workflows and sandboxes

Workflows, their versions and sandboxes live on the API (`src/api/workflows.ts`; the fake server's `workflows.ts` and `sandboxes.ts`). A workflow is stored as Lightning's document (jobs, triggers, edges, positions); `toDocument` and `fromDocument` in `src/model/workflow-document.ts` turn the canvas's graph into it and back. Every id is a UUID: seeded steps get theirs from their workflow's slug (`apiNodeId`), and a sandbox's copy from the step it was copied from (`cloneNodeId`), which is how the fixtures' run history is still drawn on the right steps. A sandbox is a child project and a copy of it: making one copies every workflow with its triggers off, and every component and environment variable (see Components), and the editor shows the selected sandbox's copy (paired by name). In a sandbox the editor saves each edit to that copy (`onSaveWorkflow`, a moment after the change), "Create promotion request" (in the sandbox chip and the Fn menu) merges it into the sandbox's parent as a new version (`onPromote`), bringing the sandbox's new and changed components and environment variables with it, and the version picker lists the snapshots. The API's rules hold: a name unique in the project, no cycles, one enabled trigger and exactly one edge out of it, triggers never removed; a refused save shows in the editor's status bar. Turning a workflow on or off switches its trigger (not a new version); deleting marks it deleted. A project's workflows are listed by `WorkflowList`, on Workflows and Overview alike (actions from `useWorkflowListActions` in `src/pages/workflow-list.query.ts`): `ListGroup`s of Published services (a workflow with a service listing, with the catalog on), Live workflows and Paused workflows, empty ones left out (`workflowSections` in `src/model/workflow-list.ts`), each row's pill saying what its switch says (Live, or a grey Paused). Make a copy is the demo's `POST /api/demo/projects/:id/workflows/:id/copies`: fresh ids, paused, named "… (copy)". "New workflow" makes one at once, in the selected sandbox. The Sandboxes page reads each sandbox's changes from the API's merge preview. A workflow's runs are still the fixtures' (`fixtureWorkflow(id)` finds its slug) until runs move to the API.

### History

History (`HistoryPage`, a project's or, with Organizations on, every project's) is Lightning's work order history: `WorkOrderEntry` rows that open to each run's `RunEntry` (steps, retry from a step, inspect in the editor), search by id, dataclip name, input or log, and Lightning's filters as a row of `FilterChip`s in `HistoryFilterBar` (workflow, status (any number), received and last activity ranges, project across projects, a work order from a link; channel and outcome on the channel requests tab), all kept in the URL by the wrapper (`HistoryFilters` and `matchesFilters` in `src/model/history.ts`, `filtersFrom`/`paramsFor` in `HistoryPage.query.tsx`), and bulk retry, retry-from and cancel by Lightning's rules (`bulkActions` in `src/model/history.ts`), with a Channel requests tab (`ChannelRequestTable`). Its work orders, runs and channel requests come from the API (`src/api/work-orders.ts`, `useChannelRequests` in `src/api/channels.ts`), the same ones the editor reads: retrying (`/work_orders/retries`) adds a run to each work order on the server, on the workflow as it now stands, and a deleted workflow's are discarded; cancelling stops runs that haven't started; a run started in the editor is recorded when it finishes (`onRunFinished`, the demo standing in for Lightning's worker). A sandbox's copy of a workflow has its own runs, none to start with. Run, work order and dataclip ids are still the demo's short ones, not UUIDs, because the pages show them whole.

### Admin settings

Admin settings (`AdminSettingsPage`, at `/admin-settings`) is Lightning's superuser area, `/settings/*`: users, every project, the audit trail, single sign-on (OIDC), every collection and maintenance. It's core Lightning, so it has no flag, and it's instance-wide, so keep it apart from Organization settings (the flagged organisation concept). Its IA node is `superuserOnly`: the route table hides it unless the shell's `isSuperuser` (your role on `GET /api/me`) is true, and waits while that's unknown, and `AccountMenu` only links to it with `showAdminSettings`. Its users, projects (with their members) and audit trail come from the API (`src/api/admin.ts`; the fake server's `users.ts`, `user-routes.ts`, `projects.ts` and `audit.ts`, seeded from `src/fixtures/admin.ts`), so a change there is what every page sees and lands in the audit trail. The audit trail is paged and filtered by the server (`useAuditTrail`), with its filters and page in the URL; only a text search reads the whole filtered trail (docs/api-gaps.md). Deletions are only ever scheduled, as the API has it: "Delete now" is left out. Every collection on the instance, the single sign-on provider and the instance itself (`useInstance`: its URL and deletion grace period) come from the API too; testing a provider before saving it and the maintenance jobs are on the demo's own routes (`/api/demo/auth_provider/test`, `/api/demo/maintenance`, `src/api/maintenance.ts`). The wrapper reads no fixtures. Helpers such as `projectOwnerError`, `authRedirectUri` and `filterAuditEvents` are in `src/model/admin.ts`. Reuse `AdminUserTable`, `UserFormModal`, `AdminProjectTable`, `ProjectFormModal`, `AuditTrail` (with `AuditChanges`), `AuthProviderForm`, `AdminCollectionTable` and `MaintenanceTaskCard`; for a long list use the `Pagination` primitive, for a typed confirmation `ConfirmModal`'s `confirmPhrase`, and for an expandable row `DataTable`'s `renderDetail`.

### Connected systems

The organisation's connected systems and their access grants are on the demo's own routes (`/api/demo/connected_systems`, `src/api/connected-systems.ts`; Lightning's API has none yet), following `api/conventions.md`. Adding one (by hand, from Systems or Overview, or from the X-Road directory) saves it and opens its page. By hand is `AddConnectedSystemFlow`: "Connect a system", the same `ConnectSystemPicker` as the editor's "Add a step" with `purpose="system"` (the categories only, no Connected, AI or Services), then a form for the picked system; the editor opens it on the form. Editing it (`SystemFormModal`: name, description, API docs, OpenAPI spec and, for a direct system, each environment's URL, keeping its credentials; given an `environment`, as each environment's Edit on the system's page opens it, just that one's URL), revoking a grant and deleting a system go through the API, and it's the same list for the editor's "Add a step". A system's `openApiSpecUrl` is linked on its page and tagged OpenAPI in the list. "Live" is a workflow's word: an X-Road system whose connection is through reads "Connected". Old slug links (`/connected-systems/dhis2/…`) redirect, in the route (`PageRoute`). So are the catalog a new system is picked from (`useAdaptorCatalog`: `/api/demo/adaptor_catalog`, sorted into the pickers' categories; `useAdaptors`: `/api/demo/adaptors`; `useSystemSuggestions`: `/api/demo/connected_systems/suggestions`, leaving out what's already connected), which Systems and Overview share, and the ecosystem map (`useEcosystem`: `/api/demo/ecosystem`), still placed by hand in `src/fixtures/ecosystem.ts`, its stations named by system id; a system that's deleted leaves it. The Systems page and its wrapper are in `src/pages/systems/`.

### Services

A project's published services are on the demo's own routes (`/api/demo/services`, `/api/demo/projects/:id/services`, `src/api/services.ts`). A service's id is a UUID (`apiServiceId`; old slug links redirect) and its code is the end of its address. Owners and admins set it Live or Draft, turn on MCP and publish it to X-Road (under its code unless it has its own); everyone else reads it, so the service page leaves those actions out. The catalog (`src/pages/services/`) lists every Live service from the API, filed under its `section` (who offers it; its project's name when it has none) with its `mcpToolName`, beside the channels the organisation's systems offer (`useSystemChannels`: `/api/demo/connected_systems/channels`), the services it uses over X-Road (its systems, named from the X-Road directory), and the organisation's MCP server (`mcpServerUrl` on `useOrganization`). The same Live services are offered as steps in the editor's "Add a step" (`StepService`, `isCallableFromStep`), so a workflow can call another's service. In the editor, the workflow behind a service lists service.yaml (`serviceYaml` in `src/model/services.ts`): its catalogue record, then, with X-Road on, the service as the Security Server registers it, in the Security Server API's own field names (`client_id`, a REST `service_description`, the service's `service_code`, `url`, `timeout`, `ssl_auth` and `endpoints`, and `access_rights` by subsystem), then how to call it.

### Organization settings

The organisation's name, your role in it and its members are on the API (`/api/organizations`, `src/api/organization.ts`; the fake server's `organizations.ts`, as openfn-3-poc's api/organizations.md has them). The demo shows the first organisation you're in, by name; someone in none gets Not Found. Admins rename it under General (`PATCH /api/organizations/:id`). Roles are Admin and Member, with no owner, and the organisation always keeps an admin (`one_admin`). Members are added by the email of someone already on OpenFn (nobody else can be invited yet), and belonging opens none of its projects; leaving takes nobody out of a project. Visibility defaults, who manages the Security Server and the logo (an image under General, sent as a data URL to `PUT /api/demo/organization/logo`: PNG, JPEG, SVG or WebP up to 256 KB, checked by `logoProblem` before it's sent; `DELETE` takes it off) are the demo's own, on `/api/demo/organization`; the rest of the X-Road identity is the X-Road operator's, read only from `GET /api/demo/organization/xroad` (`useOrganizationXRoad`, seeded from `orgXRoad`), and billing is read only. Beside Lightning the demo's own part starts at its defaults, with no X-Road identity. The page and its wrapper are in `src/pages/organization-settings/`; the organisation's types are in `src/model/organization.ts`. Admins get the page's actions; for anyone else the wrapper leaves them out and the page reads only. The members table calls a member's role their Org role. With Organizations on, the top-left corner (`InstanceLogo`, in the sidebar and the mobile top bar) is the organisation's: its name and its logo, or its initials (`instanceInitials`, which skips little words: "Ministry of Health" is MH) without one; the shell's wrapper puts it in `ShellContext`'s `organization`. Without Organizations, or while you're in none, the corner is the instance's.

### Handbook

The handbook's files are on the demo's own routes (`/api/demo/handbook`, `src/api/handbook.ts`). Anyone in an organisation adds or removes one; a file's name is unique, its type is one the handbook takes, and together they fit its capacity, with a refusal announced in a toast. The demo keeps a file's name and size, not its contents. The article is on the API too (`PUT /api/demo/handbook/article`, seeded from the fixture): Edit turns it into Markdown (`toMarkdown`/`fromMarkdown` in `src/model/handbook-markdown.ts`: `## ` sections, `- ` lists, `| Label | Detail |` facts, `[text](/path)` links), and the server refuses a section without a heading or one named twice and records who last edited it. The page and its wrapper are in `src/pages/handbook/`; the handbook's types (`Handbook`, `WikiSection`, `HandbookFile`) are in `src/model/handbook.ts`.

### X-Road

A step's type is its connected system (`JobNode.system`, the system's id on the API, saved as the job's `system_id`, a demo extension): the canvas card, the explorer row, `CodePaneHeader`'s pill, the inspector and `StepConfigPanel` name the system with its adaptor's logo, so two DHIS2 instances read as two systems, not "DHIS2" twice. Picking a system sets the adaptor, which Config shows as text, not a choice; only without connected systems (the flag off) does Config offer an adaptor picker. A step on no system (built-in tools, AI, a service call) shows its adaptor. X-Road is a property of a connected system, never of a workflow. A system's `connection` (`src/model/connected-systems.ts`; the systems themselves are in `src/fixtures/connected-systems.ts`) is direct or via X-Road (a member, subsystem and service, a status track, an agreement); routing, headers and the organisation's identity come from the organisation's X-Road settings (`orgXRoad` in `src/fixtures/xroad.ts`, which also holds the directory (`listClients`) and the network; Organization settings and a system's page read the identity from the API, and a system's page the directory too (`GET /api/demo/organization/xroad/directory`, `useXRoadDirectory`); a service's page reads the identity from the API as well). Components get the settings, the member and the service as props; helpers that read them (`clientIdOf`, `findService`, `serviceIdOf`) are pure functions in `src/model/xroad.ts`. OpenFn is always a subsystem of the owning organisation. Show how a system is reached with `ConnectionMethodBadge` (`compact` on canvas cards) and an X-Road system's access with `XRoadAccessBadge`; reuse `XRoadStatusTrack`, `XRoadConnectionDetails`, `XRoadDirectory`, `XRoadCallDetails` (who called a run over X-Road), `PublishToXRoadModal`, `ServiceRecordList` (a service's catalogue record) and `CopyValue` (any value to paste elsewhere). Name services as actions ("Verify a national ID"), not resources.

### Ecosystem view

The systems page has a List | Ecosystem switch. The ecosystem is `EcosystemView`: a transport map (`EcosystemMap`) of the organisation's systems as stations (their adaptor logos) and the workflows between them as right-angled lines with runs moving along them, with `EcosystemPanel` beside it for the whole ecosystem or the picked workflow (a line diagram, trigger first), system or link. The editor (its frame is the patterns `EditorShell`, `EditorTopBar`, `CanvasLayout`, `CodeLayout`, `EditorTray` and `EditorPanel`, everything that knows about workflows, `CodePaneHeader` and `EditorStatusBar` included, is in `src/components/domain/`, and its page is `src/pages/WorkflowEditorPage.tsx`) is laid out like an IDE: `EditorShell` (the top bar, the main surface, and the side column on the right, where the assistant lives a level above either view), `EditorToolbar` (whose groups the page puts in `EditorTopBar`: the `Fn` `WorkflowFileMenu`, the workflow title (name • version, which opens the version `Picker`), `SandboxChip` (on main "main" with a lock, since main is read-only; in a sandbox its name in amber with a count of what the copy changes against its parent, from `workflowChanges` in `src/model/workflow-changes.ts`, plus what it changes in its own components and environment variables (`componentChanges`, from the merge preview); its panel lists the changes with "Create promotion request", above the sandboxes to switch to), the Canvas/Explorer switcher, in code mode a `LoadedRunBar` for a loaded run, `TriggerStatusMenu` ("Live" or "Paused": whether the trigger starts runs where you are, with the switch and what runs there use: credentials' values for the environment, and in a sandbox its own environment variables, run history and collections), `RunMenuButton` (the main action in a sandbox; on main "Edit in sandbox" is), and the assistant toggle in its own group), then in the main surface either `CanvasLayout` (the canvas, with a bar pinned to its bottom and a card over its right) or `CodeLayout` (the code view, with its trays: `EditorPanel` under the code and an `EditorTray` for the details column on the right). On main, `ReadOnlyNotice` says the workflow is read-only: pinned to the bottom of the canvas (`CanvasLayout`'s `bottom` slot) with a link to edit in a sandbox, and as a tag in the code pane's top-right corner. **The canvas has no panel.** Pinned just above the workflow's top card (the canvas's `header`, so it pans with the workflow) sits `CanvasRunsBar`, which sets what the workflow shows: run history over a period (`PeriodPicker` with Off, 24h, 7d, 30d, plus the run and failure counts), just the workflow (Off), or a loaded run with a clear "Unload run" (`LoadedRunBar`, which goes back to the history; no Filter while a run is loaded). In a sandbox, hovering a card shows a + on its bottom edge that adds a step after it (after the trigger, the step goes in between the trigger and its first step, which moves down a row with everything below, since a trigger has exactly one edge out) through `ConnectSystemPicker` ("Add a step", in a `Modal`; the picker takes no title of its own, so a systems page can open it as "Connect a system"): a `SettingsNav` of Connected (the project's systems beside the built-in tools, the default), AI (generate, summarize, translate, classify, extract, and the models), with the Service catalog on Services (the organisation's Live webhook services, under who offers each, never the one the workflow backs; picking one adds an HTTP step named for the service whose code posts its input fields to its address, `serviceStepBody` in `src/model/services.ts`) and the categories in `src/fixtures/adaptor-catalog.ts`, which holds every adaptor; add new adaptors there, with their logo in `src/assets/adaptors/`. Clicking a card selects it and opens the inspector; double-clicking it, or its ⋮ menu's Edit, opens that node in code mode. A page like it opens with the bottom and right panels hidden; showing them from the ⋯ menu lasts while it stays open, and opening a code item brings back the remembered layout. It shows the whole workflow's run history (every version, however runs started) for the same period as the runs bar, from `workflowHealth` in `src/model/runs.ts`, with work order outcomes (`Donut`), runs and failed runs over time (`BarChart`), steps with failures and failures by reason (`FailureBreakdown`), where picking a run loads it and opens the step it failed at.

Paths (edges) are Lightning's: each has a condition (always, on success, on failure, or on match with a JavaScript expression), an optional label and a switch (`WorkflowEdge`'s `condition`, `expression`, `label`, `enabled`, saved as the edge's `condition_type`, `condition_expression`, `condition_label` and `enabled`). The canvas draws each with `EdgeBadge` (a `DiagramMarker`: the condition's glyph, the label in a tab beside it, dashed when off) and a path that's off as a dashed line; clicking a badge selects the path and opens `EdgeInspector` in the canvas's `rightOverlay` in place of the step inspector, editable in a sandbox and read-only on main. A path from a trigger is Always or On match only (`edgeConditionsFor`), and a path that's off never runs.

Run counts on the canvas must add up down the graph: `runActivity` counts a run only along the path it walked from the trigger on the graph being shown, so the trigger counts every run, each step counts exactly what its incoming connectors carried, and no count grows as the workflow goes on. Runs that didn't walk this graph from its trigger (another version, a retry from a step) are left out of the counts, totals included, and the runs bar's list says how many.

## Colours

Every colour goes through the design system: Tailwind colour utilities (`bg-*`, `text-*`, `border-*`, `fill-*`, `stroke-*`), which resolve to theme tokens the demo settings' Theme section re-skins, or a named CSS variable in `src/theme/theme.css`. ## Storybook

Every UI component and template has a corresponding `.stories.tsx` file next to it. **When you add, modify, or delete a component, you must update its Storybook story to match.** Specifically:

- **New component** → create a `.stories.tsx` file alongside it with at least a default story and any meaningful variants.
- **Changed props/API** → update the existing story args and variants to reflect the new interface.
- **Deleted component** → delete the corresponding `.stories.tsx` file.
- **Router-dependent components** → use the `withRouter` decorator from `src/stories/decorators.tsx`.
- Stories should use fixtures from `src/fixtures/` when possible rather than inventing inline fixtures.

Run `npm run build-storybook` to verify stories compile. This also runs in CI on every PR.
